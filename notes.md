## Architecture

### Modules

```text
main.rs               logging, panic hook, then app::run()
└─ app.rs             frame loop: draws the current state 30 times/s, rotates every 2 s
   ├─ config.rs       in/config.toml → AppConfig (one section per state)
   ├─ states.rs       the `State` trait
   │  └─ states/      clock · weather · calendar
   │     ├─ feed.rs   background fetching, for the network states
   │     └─ google_auth.rs   OAuth2 tokens (calendar)
   └─ matrix.rs       `Matrix`: the screen the states draw on (see "The matrix layers")

paths.rs              where the files are (config, credentials, logs): used by all
```

### Two loops that never wait for each other

```text
 frame loop (app::run)                   background task (one per network state)
 ─────────────────────                   ───────────────────────────────────────
 every 33 ms:                            loop:
   state.draw(&mut matrix)                 fetch()                ← network, may be slow
     └─ feed.latest() ◄──── Feed<T> ◄───── tx.send_replace(data)
   matrix.show()           (last value)    sleep(REFRESH_PERIOD, or retry delay)
 every 2 s:
   next_state()  (skips the states that aren't ready)
```

`draw` only reads what was already fetched: a slow or dead network never freezes the display.

Not even CPU work in a fetch (e.g. a TLS handshake) delays a frame, thanks to the second
tokio worker: see [Where the code runs](#where-the-code-runs).

### Where the code runs

```text
 main thread              tokio worker thread          other threads
 ───────────              ───────────────────          ─────────────
 app::run (frame loop)    fetch_loop of each           C++ refresh thread (drives the GPIO)
 Matrix::show waits       network state                log file writer (tracing-appender)
 for the vsync
```

`#[tokio::main]` runs `main` on the main thread. Spawned tasks run on the worker threads:
one per CPU core by default, set to 2 here (`worker_threads = 2`).

Why 2 on a single-core Pi Zero: the frame loop's timer is fired by a worker, not by the
main thread (which just sleeps in `block_on`). With one worker, CPU work in a fetch (a TLS
handshake: tens of ms) would leave nobody to fire the tick, and the frame would be late.
With two, the idle one fires it on time, and the kernel preempts the busy one to run the
frame loop. To reproduce the Pi's default on the PC: `TOKIO_WORKER_THREADS=1 make sim`.

### The matrix layers

```text
 states ── embedded-graphics ──► Matrix                  display.rs   double buffering
                                   │                     (simulator.rs replaces it on the PC)
                                   ▼
                  RgbLedMatrix, Canvas, Font             wrapper.rs   safe API, 1:1 with C
                  + DrawTarget for Canvas                graphics.rs
                                   │ unsafe calls
                                   ▼
                  ffi::led_matrix_create...              ffi.rs       generated by bindgen
                                   │
                                   ▼
                  librgbmatrix.a (C++)                   built by build.rs
```

Each layer only talks to the one below it. The `unsafe` code stays in `wrapper.rs`, plus
one `unsafe fn` call in `display.rs` (and `libc::raise` in the simulator). See
[FFI and unsafe](#ffi-and-unsafe).

### Private fields keep the inside free to change

*In the code:* `Feed`, `GoogleAuth`, `Canvas`, `Font`, `RgbLedMatrix`, the config structs

A struct with private fields can only be built and used through its methods:

- a `Feed` is only built by `Feed::spawn`, and read through `Feed::latest`: the channel
  inside can change without touching any state;
- `GoogleAuth` hides `yup-oauth2`: the rest of the app doesn't depend on it;
- the wrapper types protect their invariant (a valid pointer, see [FFI and unsafe](#ffi-and-unsafe)).

### Adding a state

1. Create `src/states/foo.rs`, with:
   - `FooConfig`: `#[derive(Debug, Deserialize)]`, `#[serde(default)]`, and an
     `impl Default`;
   - `FooState`, implementing `State`, built by `FooState::new(config, ...) -> Option<Self>`
     (`None` when disabled);
   - for network data, a `FooFetcher` implementing `Fetcher`, given to `Feed::spawn`.
2. Declare it in `states.rs`: `pub mod foo;`.
3. Add `foo: FooConfig` to `AppConfig`, and a `[foo]` section to `in/config.toml`.
4. Add a block in `build_states` (app.rs): its place sets the display order.

A color, font or style used by several states belongs in a shared module (e.g.
`src/ui.rs`, to create with the first one), not copied in each state.

## Ownership and borrowing

### `let _guard` keeps a value alive, `let _` drops it

*In the code:* `main` (`_log_guard`)

```rust
let _log_guard = init_logging()?; // lives until the end of `main`
let _ = init_logging()?;          // dropped at once: the last log lines would be lost
```

`_` is not a variable: the value is never bound, so it is dropped at the end of the
statement. `_log_guard` is a real variable, the `_` only silences the "unused" warning.
Use it for *guards*: values whose `Drop` does the work (flush a file, release a lock...).

### Statics are never dropped

*In the code:* `init_logging` (returns the guard instead of storing it)

Rust never runs `Drop` for a `static`. A log guard kept in a static would never flush its
last lines: `main` owns it instead.

### Drop order

*In the code:* `Matrix` (display.rs), `impl Drop for RgbLedMatrix`

- Struct fields are dropped in **declaration order**, local variables in **reverse** order.
- A type's own `Drop::drop` runs **before** its fields are dropped.

So in `Matrix`, `offscreen` (declared first) goes before `rgb_matrix`, which frees it.
And `RgbLedMatrix::drop` deletes the C++ matrix while `options`, whose strings C++ points
to, is still alive.

### Borrowing two fields at once

*In the code:* `App::draw`

```rust
self.states[self.current].draw(&mut self.matrix);
```

The compiler tracks borrows per field: `self.states` and `self.matrix` can be borrowed
mutably at the same time. Only with direct field access: a method like
`self.current_state()` borrows the whole `self`, and the line wouldn't compile.

### Moving parts out of a struct

*In the code:* `build_states` (`config.clock`, `config.weather`...)

`build_states` owns `config`, so it can move each field out to its state (a *partial
move*): no clone needed. `config` can't be used as a whole afterwards. Allowed because
`AppConfig` doesn't implement `Drop`.

### `move` closures

*In the code:* `log_panics`

The panic hook outlives `log_panics`, so its closure can't borrow `default_hook`: `move`
makes the closure take ownership of it.

### `'static` means "owns its data", not "lives forever"

*In the code:* `Fetcher: Send + 'static`, `ForecastFetcher`, `EventsFetcher`

`T: 'static` means `T` holds no borrowed reference (except `&'static` ones). A spawned
task can outlive the function that started it, so everything it uses must be owned: each
fetcher holds its own clone of the HTTP client, not a `&Client`.

### Take `Option<&T>`, not `&Option<T>`

*In the code:* `opt_c_ptr`, `RgbLedMatrix::new`, `log_events`

`Option<&CStr>` accepts any optional borrowed string, `&Option<CString>` forces the
caller to own an `Option<CString>`. Convert with `as_deref`:

```rust
options.hardware_mapping.as_deref() // &Option<CString> → Option<&CStr>
```

Same idea as taking `&str` rather than `&String`, or `&[T]` rather than `&Vec<T>`
(`log_events(events: &[Event])`).

### Cheap clones: `Arc` and handles

*In the code:* `Feed::latest` (`Arc::clone`), `AppContext::client`

`Arc::clone(&data)` only increments a counter: the data is shared, never copied. Writing
`Arc::clone(&x)` rather than `x.clone()` shows that the clone is cheap.

A reqwest `Client` already has an `Arc` inside: its clones are cheap, and share the same
connection pool. Wrapping it in another `Arc` would add nothing.

## Error handling

### anyhow: `?`, `context` and `with_context`

*In the code:* everywhere (`AppConfig::load`, `GoogleAuth::new`...)

The app uses `anyhow::Result<T>` (= `Result<T, anyhow::Error>`): a single error type that
any error converts into with `?`. Libraries rather use `thiserror`, to give their callers
precise error types.

`context` wraps an error with what was being done:

```rust
fs::read_to_string(&path).context("failed to read the config")?;
fs::read_to_string(&path).with_context(|| format!("failed to read {}", path.display()))?;
```

`with_context` takes a closure: the `format!` only runs if there is an error.

Error messages are lowercase, without a final period: they get chained
(`failed to read in/config.toml: No such file or directory (os error 2)`).

### Printing errors: `{e}`, `{e:#}`, `{e:?}`

*In the code:* `{e:#}` in every log of an error

| Format  | Prints                                                                  |
|---------|-------------------------------------------------------------------------|
| `{e}`   | the last context only: `failed to read in/config.toml`                  |
| `{e:#}` | the whole chain, on one line: `failed to read in/config.toml: No such file or directory (os error 2)` |
| `{e:?}` | the whole chain on several lines (`Caused by:`), and the backtrace if enabled |

### Returning `Result` from `main`

*In the code:* `main`

When `main` returns `Err`, Rust prints it (with `{:?}`) and the process exits with code 1:
systemd knows it failed. Cleaner than a panic.

### Log and carry on: `inspect_err`, `unwrap_or_default`, `.ok()?`

*In the code:* `AppConfig::load_or_default`, `CalendarState::new`, `main`

```rust
Self::load()
    .inspect_err(|e| warn!("...: {e:#}")) // sees the error, without consuming it
    .unwrap_or_default()                  // Err → AppConfig::default()

GoogleAuth::new()
    .await
    .inspect_err(|e| error!("...: {e:#}"))
    .ok()?; // Result → Option, then `?` returns `None` from `CalendarState::new`
```

`?` also works on an `Option`, in a function returning an `Option`.

### `context` on an `Option`, and `bail!`

*In the code:* `GoogleAuth::token`, `Font::load`, `RgbLedMatrix::new`

```rust
token.token().context("OAuth2 token is empty")?;     // None → error with this message
bail!("failed to load font from {}", path.display()); // = return Err(anyhow!(...))
```

### Prefer the constructors that return an error

*In the code:* `init_logging` (`try_init`), `AppContext::new` (`Client::builder()`)

`init()` (tracing-subscriber) and `Client::new()` (reqwest) panic when they fail.
`try_init()` and `Client::builder().build()` return an error instead, which `?`
propagates, with some context.

### Two failures, one path: `timeout` + `flatten`

*In the code:* `fetch_loop`

```rust
let result = timeout(F::TIMEOUT, fetcher.fetch()) // fetch: Future<Output = Result<Data>>
    .await                // Result<Result<Data>, Elapsed>: the outer `Err` means "timed out"
    .context("timed out") // Result<Result<Data>>: both levels are anyhow errors
    .flatten();           // Result<Data>
```

A fetch that hangs and a fetch that fails then go through the same `match`.

### HTTP errors aren't Rust errors: `error_for_status`

*In the code:* `ForecastFetcher::fetch`, `EventsFetcher::fetch`

For reqwest, a `404` or `401` response is a success: the request went through.
`error_for_status()` turns the 4xx and 5xx statuses into errors. Without it, the body of
the error would be parsed as data. For Google, an error has no `items`: it would silently
look like "no event".

### `Infallible` and `let Ok(()) = ...`

*In the code:* every `State::draw`, `Matrix::show` (simulator.rs)

Drawing on the matrix can't fail: its `DrawTarget::Error` is `Infallible`, an enum without
any variant. No value of it can exist, so the compiler knows `Err` can't happen, and the
pattern needs no `else`:

```rust
let Ok(()) = matrix.clear(Rgb888::GREEN); // clear: Result<(), Infallible>
let Ok(_) = text.draw(matrix);            // Text::draw: Ok(position after the text)
```

Better than `.unwrap()` (which suggests a possible panic) or `let _ =` (which would
silently ignore a real error): if the error type ever becomes fallible, this stops
compiling.

### When to panic

*In the code:* `EXECUTABLE_DIR` (`expect`), build.rs, `log_panics`

`expect("...")` is for what can't fail in practice, or where nothing can be done anyway
(the executable's own path, the build script). Everything else returns an error.

The message says what *should* have been true, in lowercase: the style recommended by the
std docs (`Result::expect`). The panic prints it before the error, so it reads naturally:

```text
thread 'main' (…) panicked at build.rs:62:10:
make should be installed: Os { code: 2, kind: NotFound, message: "No such file or directory" }
```

By default, Rust only prints a panic to stderr: the hook set by `log_panics` also logs it.

## Traits and generics

### Trait objects: `Box<dyn State>`

*In the code:* `App::states`, `build_states`

A `Vec` holds values of a single type. `Box<dyn State>` is that type: a pointer to "some
type implementing `State`", plus a table of its methods (the *vtable*). Each call
(`state.draw(...)`) is resolved at runtime: *dynamic dispatch*.

```rust
let mut states: Vec<Box<dyn State>> = Vec::new(); // the annotation matters:
states.push(Box::new(clock));                     // Box<ClockState> → Box<dyn State>
```

Without the annotation, the first `push` would make it a `Vec<Box<ClockState>>`, and the
second one wouldn't compile.

### Generics: `Feed<T>`, `fetch_loop<F: Fetcher>`

*In the code:* `Feed`, `Feed::spawn`, `fetch_loop`

Generic code is written once, and the compiler generates a copy for each type it is used
with (*monomorphization*): `Feed<Forecast>`, `Feed<Vec<Event>>`. Calls are resolved at
compile time (*static dispatch*), and can be inlined.

|                                    | `dyn Trait` (`State`)         | generics (`Fetcher`)               |
|------------------------------------|-------------------------------|------------------------------------|
| call resolved                      | at runtime (vtable)           | at compile time (a copy per type)  |
| different types in one `Vec`       | yes                           | no                                 |
| associated consts, `-> impl Trait` | not allowed                   | allowed                            |
| used for                           | the rotation of the states    | each feed, which knows its fetcher |

`Fetcher` couldn't be used as `dyn Fetcher` anyway: a trait with associated consts, or
methods returning `impl Trait`, isn't *dyn compatible*.

### Associated types and consts

*In the code:* `Fetcher` (`Data`, `NAME`, `REFRESH_PERIOD`, `MAX_AGE`, `TIMEOUT`)

Each implementation picks them once:

```rust
impl Fetcher for EventsFetcher {
    type Data = Vec<Event>;
    const REFRESH_PERIOD: Duration = Duration::from_mins(5);
    const TIMEOUT: Duration = Duration::from_mins(2); // replaces the default value
    // ...
}
```

Generic code then uses them as `F::Data`, `F::NAME`... An associated const can have a
default value in the trait (`TIMEOUT`): an implementation only declares it to change it.

### `Fetcher<Data = T>`, and repeated bounds

*In the code:* `Feed::spawn`

`F: Fetcher<Data = T>` means "any fetcher whose `Data` is the `T` of this feed". The trait
declares `type Data: Send + Sync + 'static`, but the compiler doesn't carry these bounds
over to `T` through `Data = T`. Without `T: Send + Sync + 'static` in the `where` clause,
it fails with "`T` cannot be shared between threads safely".

### `async fn` in traits, and `+ Send`

*In the code:* `Fetcher::fetch`

An `async fn` is a function returning a `Future`. These two are the same:

```rust
async fn fetch(&mut self) -> Result<Self::Data>;
fn fetch(&mut self) -> impl Future<Output = Result<Self::Data>>;
```

`tokio::spawn` needs a `Send` future (the task may move to another thread), and an
`async fn` declared in a trait can't promise that. So the trait uses the second form, with
`+ Send`. Implementations still write `async fn fetch(&mut self)`, and the compiler checks
that their future is `Send`.

### `&mut self`, `Send` and `Sync`

*In the code:* `Fetcher::fetch`

- `Send`: the value can be moved to another thread.
- `Sync`: the value can be used from several threads at once (through `&`).

The task owns its fetcher, so `fetch(&mut self)` costs nothing, and lets a fetcher keep
some state between two fetches. It also asks less of the fetcher: a future holding a
`&mut F` is `Send` when `F: Send`, while one holding a `&F` would need `F: Sync`.

### `From` gives `Into` for free

*In the code:* `From<DailyData> for Forecast`, `From<Rgb888> for Color`

Implement `From` rather than `Into`: the standard library then provides `Into`.

```rust
let forecast = Forecast::from(response.daily);
self.set_pixel(point.x, point.y, color.into()); // Rgb888 → Color, inferred from set_pixel
```

### Same method name in a type and a trait

*In the code:* `OriginDimensions for Canvas`, `OriginDimensions for Matrix`, `DrawTarget::clear` for `Matrix`

`Canvas` has its own (*inherent*) `size()` and `clear()`, and gets trait methods with the
same names from `embedded-graphics`. Inherent methods win, so the trait ones must be
called with the trait's name (*fully qualified*):

```rust
canvas.size()                          // inherent: (i32, i32)
OriginDimensions::size(&canvas)        // trait: Size
canvas.clear()                         // inherent: black only (`canvas.clear(RED)` doesn't compile)
DrawTarget::clear(&mut canvas, RED)    // trait: any color
```

That's also why `OriginDimensions::size` for `Canvas` can call `Canvas::size(self)`
without calling itself.

The same syntax names a trait's associated type:
`<DefaultHyperClientBuilder as HyperClientBuilder>::Connector` (google_auth.rs).

### Extension traits: `use` brings methods

*In the code:* `MetadataExt` (display.rs), `SubscriberExt`, `SubscriberInitExt`, `IsTerminal` (main.rs), `anyhow::Context`

A trait's methods only exist where the trait is in scope. Some traits exist only to add
methods to an existing type:

```rust
use std::os::unix::fs::MetadataExt; // adds uid() and gid() to `Metadata` (Unix only)
use anyhow::Context;                // adds context() to `Result` and `Option`
```

A "method not found" error often means a missing `use`. Preludes
(`embedded_graphics::prelude::*`) import a crate's usual traits at once, but not all of
them: `measure_string` (clock.rs) needs `use embedded_graphics::text::renderer::TextRenderer`.

### Implementing a library's trait: `DrawTarget`

*In the code:* graphics.rs, `Matrix` (display.rs, simulator.rs)

`embedded-graphics` draws anything (shapes, text, images) on any type implementing its
`DrawTarget` trait. A target only provides:

- its size, through `OriginDimensions` (`Origin`: the drawable area starts at (0, 0)),
- `draw_iter`, which sets pixels.

Every other method has a default implementation, built on these two. `clear` is still
overridden: the C library fills the whole canvas in one call, instead of one per pixel.

*Orphan rule*: a crate can implement a trait for a type only if the trait or the type is
its own. `impl From<Rgb888> for Color` is allowed because `Color` (generated by bindgen)
belongs to this crate.

### Text with u8g2 fonts: measure, then draw

*In the code:* `TIME_STYLE`, `DATE_STYLE`, `draw_time`, `centered_start` (clock.rs)

`embedded-graphics`' own fonts (`mono_font`) are all monospace. The `u8g2-fonts` crate
brings the ~2000 fonts of the u8g2 C library, made for small screens, through
`U8g2TextStyle`, a text style for `Text` like `MonoTextStyle`. Only the fonts used end up
in the binary. The name's suffix tells the characters: `_tf` all of Latin-1 (é, °), `_tr`
ASCII only (the others are skipped), `_tn` digits only, `_m*` monospace.

A text style implements `TextRenderer`: `measure_string(text, position, baseline)` returns
where the next character would start (`next_position`) and the pixels the text covers
(`bounding_box`), without drawing. Measuring first allows layouts that `Text`'s alignment
can't do:

- **Centered on the digits**: `Baseline::Middle` centers the font's whole height, with
  the room for the letters below the line (g, p): the texts sat too high. `centered_start`
  centers the pixels of a `0` instead.
- **Leaning toward the middle**: 5-px digits in a 16-px half can't be exactly centered
  (5.5 px on each side). The time leans down and the date up (`AnchorY`): the same
  margin at the top and bottom edges.
- **A blinking colon that doesn't shift the text**: in a proportional font, a space isn't
  as wide as the colon. `time` always keeps its colon; without it, `draw_time` draws hours
  and minutes apart, the minutes where `HH:` ends.

### `Default`: derive it or write it

*In the code:* `AppConfig` (derived), `ClockConfig`, `WeatherConfig`, `ClockState` (written)

`#[derive(Default)]` gives each field its own default (`0`, `false`, `String::new()`...).
When another value is needed (`enabled: true`), or a field has no `Default` (`Instant`,
in `ClockState`), implement `Default` by hand.

`..Default::default()` fills the fields that aren't listed:

```rust
MatrixOptions { rows: 32, cols: 64, ..Default::default() }
```

## Async and tokio

### Futures are lazy, tasks run

*In the code:* `Feed::spawn`, `main`

Calling an async function only builds a future: nothing runs until it is `.await`ed, or
handed to `tokio::spawn`, which runs it as an independent *task*:

```rust
tokio::spawn(fetch_loop(fetcher, tx)); // returns at once, the loop runs in the background
```

A spawned task may run on another thread, and outlive its caller: it must be
`Send + 'static`. `#[tokio::main]` runs the body of `main` on the main thread
(`block_on`): the frame loop isn't spawned, so it doesn't need to be `Send`.

### Never block a task

*In the code:* `State::draw`, `fetch_loop`

A task only lets the others run when it reaches an `.await`. A blocking call
(`std::thread::sleep`, `std::fs`...) or a long computation inside async code freezes every
task of its thread. Use the async versions (`tokio::time::sleep`, reqwest), or
`tokio::task::spawn_blocking` for heavy work.

`Matrix::show` does block until the vsync, but on the main thread, where it only delays
the frame loop itself.

### A steady frame rate: `interval` rather than `sleep`

*In the code:* `app::run` (`frame_clock`)

```text
sleep(33 ms) after drawing   |draw|---33 ms---|draw|---33 ms---|   period = 33 ms + draw: drifts
interval(33 ms)              |draw|-----------|draw|-----------|   ticks at start + n × 33 ms
```

- `MissedTickBehavior::Skip`: after a slow frame, the missed ticks are dropped. The
  default (`Burst`) would draw them all in a row to catch up.
- The first `tick()` completes at once.

### `select!`: the first one wins

*In the code:* `app::run`, `fetch_loop`

```rust
tokio::select! {
    _ = sleep(delay) => {}     // runs the branch of the first future to complete...
    _ = tx.closed() => return, // ...and drops the other ones
}
```

Dropping a future cancels it: only use futures that lose nothing when dropped (*cancel
safe*), like these ones. When several are ready at once, the branch is picked at random,
unless the `select!` starts with `biased;`: the branches are then polled in order. `app::run`
uses it, with the signals first, so a stop signal always wins over the next frame.

### Unix signals

*In the code:* `app::run`, `Matrix::show` (simulator.rs)

`systemctl stop` sends SIGTERM, Ctrl+C sends SIGINT. Once tokio listens to a signal, the
signal no longer kills the process: it is only delivered to the stream, and the frame loop
stops cleanly (the matrix is dropped, which turns the panel off). Hence registering them
before anything else.

Closing the simulator window raises a SIGINT, so the app stops the same way.

### `watch` channel: the latest value only

*In the code:* `Feed`, `fetch_loop`

| channel     | keeps                          | fits                                   |
|-------------|--------------------------------|----------------------------------------|
| `mpsc`      | every message, in order        | a queue of jobs                        |
| `watch`     | the last value only            | a state, whose readers want the latest |
| `broadcast` | every message, for each reader | events for several readers             |

The task owns the `Sender`, the `Feed` owns the `Receiver`:

- `send_replace` stores the new value, and never fails (`send` fails once no receiver is left);
- `borrow()` reads the value without waiting, but holds a read lock while the reference
  lives: keep it short, never across an `.await`. `Feed::latest` clones the `Arc` and
  releases the lock within the statement;
- `closed()` completes once every `Receiver` is dropped: the task stops when its state is gone.

### `Instant` vs the time of day

*In the code:* `Fetched::fetched_at`, `app::run`, `ClockState::draw`

`Instant` is a monotonic clock: it never jumps, even when the system clock is set (the Pi
has no battery-backed clock, and syncs with NTP after boot). Use it for durations and ages.
Use the time of day (`chrono::Local::now()`) only to show it.

The clock's animation is timed by an `Instant` too: the position in the current loop is
`started.elapsed().div_duration_f64(EARTH_LOOP_PERIOD).fract()`, a number in `0.0..1.0`
(`fract` drops the whole loops already made).

### Timeout and exponential backoff

*In the code:* `fetch_loop`, `Fetcher::TIMEOUT`, `FIRST_RETRY_DELAY`

`timeout(duration, future)` gives up on a future that takes too long (e.g. wifi lost
during a request). After a failure, the next fetch comes sooner than a normal refresh, and
the wait doubles after each failure in a row, up to `REFRESH_PERIOD`: 30 s, 1 min, 2 min...
A network down for hours then costs a few log lines, not thousands.

## Serde and the config

### Only the declared fields are read

*In the code:* `WeatherResponse`, `CalendarResponse`, `Event`

`#[derive(Deserialize)]` reads the fields of the struct, and ignores the other ones of the
JSON (unless `#[serde(deny_unknown_fields)]`): declare only what you use.

A missing field is an error, except for an `Option` (→ `None`, e.g. `Event::description`)
or a field with a default.

### `#[serde(default)]`

*In the code:* `AppConfig`, `ClockConfig`, `WeatherConfig`, `CalendarConfig`, `Event::title`, `CalendarResponse::items`

- On a **struct**: a missing field takes its value from the struct's `Default`. A partial
  config stays valid:

  ```toml
  [weather]
  latitude = 48.85   # `enabled` and `longitude`: from WeatherConfig::default()
  ```

- On a **field**: a missing field takes the default of its type (`String::new()`,
  `Vec::new()`).

### `deny_unknown_fields`: typos in the config

*In the code:* `AppConfig`, `ClockConfig`, `WeatherConfig`, `CalendarConfig`

Two opposite choices, on purpose:

- **API responses** ignore unknown fields: an API may add fields at any time, and that
  must not break the app.
- **The config** refuses them: with `#[serde(default)]` alone, a typo would be silently
  ignored, and the field would keep its default value:

  ```toml
  [weather]
  enabeld = false   # typo: the weather would stay on, without any message
  ```

With `#[serde(default, deny_unknown_fields)]`, the config fails to load, and the warning
names the key and its line:

```text
No config loaded, using defaults: failed to deserialize .../in/config.toml:
TOML parse error at line 5, column 1
  |
5 | enabeld = false
  | ^^^^^^^
unknown field `enabeld`, expected one of `enabled`, `latitude`, `longitude`
```

The same goes for an unknown section (`[wether]`): it is checked on `AppConfig`.

### `rename`

*In the code:* `Event::title` (`"summary"`), `EventStart::At` (`"dateTime"`)

Gives a field a Rust name that differs from its JSON name.

### `untagged` enums

*In the code:* `EventStart`

serde tries each variant in order, and keeps the first one matching the JSON:

```text
{ "dateTime": "2026-11-15T18:30:00+01:00", "timeZone": "Europe/Paris" }  → EventStart::At
{ "date": "2026-11-15" }                                                → EventStart::AllDay
{ }                                                                     → error
```

The error message is vague ("data did not match any variant of untagged enum"), but the
shape is checked by the type.

### Let the types check the data

*In the code:* `DailyData` (`[f32; 1]`), `EventStart`

The weather API returns a list for each value, with one element per day. A fixed-size
array makes serde check the length (`[]` and `[1.0, 2.0]` are both refused), so
`daily.weather_code[0]` can't panic. With a `Vec`, the check would have to be done by hand.

Same with the chrono types (`DateTime<Local>`, `NaiveDate`, thanks to chrono's `serde`
feature): an invalid date is refused while parsing, not found later.

### One config section per state

*In the code:* config.rs, `ClockConfig`, `WeatherConfig`, `CalendarConfig`

Each state declares its config in its own module, with private fields: only the state
reads them. `AppConfig` only gathers the sections, and `build_states` moves each one into
its state.

## FFI and unsafe

### The safe wrapper pattern

*In the code:* matrix.rs, wrapper.rs

```text
ffi.rs       generated, unsafe, C-shaped    private to `matrix`
wrapper.rs   safe API, `unsafe` inside      each `unsafe` block justified
display.rs   the app's `Matrix`             no FFI call
```

The rest of the app can't misuse the C library: the `unsafe` code is small, in one file,
and reviewed once.

### `unsafe` blocks and `// SAFETY:` comments

*In the code:* every `unsafe` block, `undocumented_unsafe_blocks` (Cargo.toml `[lints.clippy]`)

`unsafe` doesn't turn off the borrow checker. It allows a few more operations (calling an
`unsafe fn` like a C function, dereferencing a raw pointer...), whose correctness the
compiler can't check. The `// SAFETY:` comment says why the operation is correct, and
clippy warns when it is missing.

### `unsafe fn` and `# Safety`

*In the code:* `RgbLedMatrix::create_offscreen_canvas`, `Matrix::new`

An `unsafe fn` has a contract that its caller must keep, written in its `# Safety` doc
section. The caller wraps the call in `unsafe { }`, with a `// SAFETY:` comment saying why
the contract holds.

Since edition 2024, the body of an `unsafe fn` is no longer one big `unsafe` block: each
unsafe operation inside needs its own `unsafe { }` (the `unsafe_op_in_unsafe_fn` lint
warns otherwise).

### The invariant of a handle

*In the code:* `Canvas`, `Font`, `RgbLedMatrix`

Each wrapper type states its *invariant*: `ptr` is never null, and only freed once, by
`Drop`. The constructor ensures it (`ptr.is_null()` → error, when C can return null), the private field keeps the
rest of the code from breaking it, and every `// SAFETY:` comment relies on it ("`ptr` is
valid (see `Canvas`)").

### Why the canvas doesn't borrow the matrix

*In the code:* `create_offscreen_canvas`, `Matrix`

The C library frees the canvas with the matrix. The safe way would be a lifetime: a
`Canvas<'m>` borrowing the matrix. But `Matrix` stores both side by side, and a struct
can't hold a reference to its own field (*self-referential struct*). So
`create_offscreen_canvas` is an `unsafe fn`, and `Matrix` keeps the rule by never letting
its canvas out.

### C strings: `CString`, `CStr`, `c"..."`

*In the code:* `MatrixOptions`, `Font::load`, `Canvas::draw_text`, `Matrix::new`

| Rust              | C             |                                               |
|-------------------|---------------|-----------------------------------------------|
| `String`, `&str`  |               | UTF-8, no NUL at the end                      |
| `CString`         | `char*`       | owned, ends with a NUL byte                   |
| `&CStr`           | `const char*` | borrowed, ends with a NUL byte                |
| `c"adafruit-hat"` | literal       | a `&'static CStr`, checked at compile time    |

`CString::new` fails if the text contains a NUL byte. Keep the `CString` alive as long as
C uses its pointer:

```rust
let c_text = CString::new(text)?;
ffi::draw_text(..., c_text.as_ptr(), ...); // OK: `c_text` lives until the end of the scope

let ptr = CString::new(text)?.as_ptr();    // BUG: the CString is dropped at the end of this line
ffi::draw_text(..., ptr, ...);             // dangling pointer
```

- Moving a `CString` moves its handle, not its heap buffer: the pointers given to C stay
  valid when `options` is moved into `RgbLedMatrix`.
- A path isn't always valid UTF-8: `Font::load` passes its raw bytes (`as_encoded_bytes`).

### Zeroed C structs

*In the code:* `RgbLedMatrix::new`

`std::mem::zeroed()` creates a value whose bytes are all zero. Only valid for types where
zero is a valid value, like these C structs (numbers, bools, null pointers). Never for
references, `Box`, `NonNull`...: undefined behavior.

### `Send`, `Sync` and raw pointers

*In the code:* `unsafe impl Send for Canvas`, `unsafe impl Send for RgbLedMatrix`

Raw pointers are neither `Send` nor `Sync`, so a struct holding one isn't either.
`unsafe impl Send` is a promise to the compiler: moving the value to another thread is
fine (the C++ matrix isn't tied to the thread that created it). No `Sync`: it is never used
from two threads at once.

Today, nothing needs `Matrix` to be `Send`: the frame loop runs on the main thread. These
impls only matter if the matrix ever moves into a spawned task.

### Things to know about the C library

*In the code:* `MatrixOptions`, `RuntimeOptions`, `runtime_options`, `RgbLedMatrix`

- **`0` means "library default"**, not zero: the C API only copies the non-zero fields
  (`OPT_COPY_IF_SET` in `led-matrix-c.cc`). `brightness: 0` runs at 100. To really turn
  something off, use `-1` (e.g. `drop_privileges`).
- **Root is needed** to access the GPIO. Right after creating the matrix, the library drops
  root privileges, by default for the `daemon` user. `runtime_options` picks the owner of
  the app directory instead, so the app can still write its logs and tokens.
- **Each offscreen canvas allocates a framebuffer**, only freed with the matrix: create one
  at startup, never one per frame.
- **`swap_on_vsync` blocks** until the next refresh, and gives back the buffer that was
  shown (*double buffering*, see the diagram of `Matrix::show`). Drawing on a hidden
  buffer avoids flickering.
- **The matrix keeps pointers to the option strings**: `RgbLedMatrix` keeps `options`
  alive as long as it lives.

## Compile time: consts, cfg and macros

### `const` values, built at compile time

*In the code:* `FRAME_PERIOD`, `TIME_STYLE`, `DATE_STYLE`, `PANEL_SIZE`, `EARTH`

A `const` is computed by the compiler, and costs nothing at runtime. It can only call
`const fn`s: `Duration::from_nanos` and `U8g2TextStyle::new` are. The text styles are ready
before the first frame. (`U8g2TextStyle` is `Clone` but not `Copy`: harmless for a `const`,
as each use makes a new value.)

### Compile-time checks: `const { assert!(...) }`

*In the code:* `Feed::spawn`, clock.rs (after `NB_EARTH_FRAMES`)

A `const` block in a generic function is evaluated at compile time, for each type the
function is used with: a fetcher whose `MAX_AGE` isn't longer than its `REFRESH_PERIOD`
doesn't build.

Outside of a function, the same check is a `const` with no name (`_`) and no value (`()`):
an `EARTH` image that isn't a strip of panel-sized frames doesn't build.

```rust
const _: () = assert!(condition, "message");
```

The `>` of `Duration` comes from a trait (`PartialOrd`), and trait methods can't be called
in a `const` context yet: the check compares `as_nanos()`, plain integers.

### `static` and `LazyLock`

*In the code:* `EXECUTABLE_DIR`

A `static` is a single value for the whole program, normally built at compile time.
`LazyLock` builds it at runtime instead, on first use (once, even with several threads),
then shares it.

### Images embedded in the binary: `include_bytes!` + `const fn`

*In the code:* `EARTH`, `NB_EARTH_FRAMES`, `ClockState::draw` (clock.rs), `PANEL_SIZE`

`include_bytes!("path")` pastes a file into the binary as a `&'static [u8]` (path relative
to the source file). Nothing to deploy with the app, and no file to read at runtime.

`Bmp::from_slice` is a `const fn`, so the image is parsed by the compiler. `?` and
`.unwrap()` aren't allowed in a `const` yet, hence the `match`, where `panic!` turns an
invalid image into a build error:

```rust
const EARTH: Bmp<'static, Rgb888> =
    match Bmp::from_slice(include_bytes!("../../assets/clock/earth.bmp")) {
        Ok(bmp) => bmp,
        Err(_) => panic!("assets/clock/earth.bmp should be a valid BMP image"),
    };
```

`Bmp` only borrows the bytes, and decodes the pixels while drawing: cheap for a 24-bit BMP
(3 bytes copied per pixel). The images are made by the Python scripts of `tools/`, into
`assets/`: `python3 tools/earth.py` (needs Pillow). The scripts are in git, their data isn't
(downloaded: see each script's docstring).

An animation is a *strip*: its frames stacked in one image. The clock's `EARTH`: 480
frames of 64x32 (the whole panel), one loop (40 s, `EARTH_LOOP_PERIOD`) = one Moon orbit =
two Earth turns, made by `tools/earth.py`: the Earth with satellite land colors (NASA Blue
Marble) and changing clouds, the Moon, the Sun pulsing with sunspots, stars and the Milky
Way. The number of frames is the image's height divided by the panel's, at compile time:
`as_raw().header()` is a `const fn`, and the panel's size is the `PANEL_SIZE` const of
matrix.rs. The script stays the only place to change it (with `EARTH_LOOP_PERIOD`, to keep
12 frames/s).

A loop must not jump from its last frame to its first: everything that moves makes a whole
number of cycles per loop (Earth turns, Sun turns, the pulse's sine waves, the clouds'
changes).

To draw one frame, `GetPixel::pixel` reads only its 2048 pixels. `sub_image` would be the
obvious tool, but tinybmp implements it by decoding the whole strip, and clipping away all
the other frames (480x more work).

Size: 6 KB per frame at 24 bits, 2.9 MB for `EARTH`. If it ever matters, a 256-color BMP
(8 bits, read by tinybmp too) would divide it by 3.

### `#[cfg]` and Cargo features

*In the code:* matrix.rs (`simulator`), Cargo.toml `[features]`, the `tests` modules

`#[cfg(...)]` only compiles the item below it when its condition is true:

```rust
#[cfg(not(feature = "simulator"))]
pub use display::Matrix;
#[cfg(feature = "simulator")]
pub use simulator::Matrix;
```

Exactly one `Matrix` exists, chosen at compile time: no runtime cost, and the Pi build
contains no simulator code. Its dependencies are `optional`, and enabled by the feature
(`dep:embedded-graphics-simulator`). `#[cfg(test)]` compiles a module for `cargo test` only.

### Compile-time macros: `env!`, `concat!`, `include!`

*In the code:* `AppContext::new` (user agent), `APP_NAME`, ffi.rs

- `env!("CARGO_PKG_VERSION")` reads an environment variable while compiling (Cargo sets
  the package name, version, binary name `CARGO_BIN_NAME`...): the name is written once,
  in Cargo.toml.
- `concat!` joins literals into a single `&'static str`: `"pixel/0.1.0"`.
- `include!` pastes a file's content: ffi.rs includes the bindings written by bindgen in `OUT_DIR`.

### `#[rustfmt::skip]`

*In the code:* `Condition::from_wmo`

Tells `cargo fmt` to keep an item as written: here, a `match` aligned like a table.

## Small idioms

### `Self` inside an `impl`

*In the code:* the constructors (`App::new`, `Feed::spawn`...), the `Default` impls,
`Condition::from_wmo`

Inside an `impl` block, `Self` is the type being implemented: write `Self { .. }`,
`Self::Clear`, `Self::default` rather than repeating the type's name.

```rust
impl Condition {
    fn from_wmo(code: u8) -> Self {
        match code {
            0 | 1 => Self::Clear, // rather than Condition::Clear
            // ...
```

- Renaming the type only changes its `impl` lines, not every constructor and variant.
- clippy can list the repetitions: `cargo clippy -- -W clippy::use_self`.

One exception, on purpose: `OriginDimensions::size` for `Canvas` calls `Canvas::size(self)`,
the inherent method (see [Same method name in a type and a trait](#same-method-name-in-a-type-and-a-trait)).
`Self::size(self)` would call the same method, but would read like the function calling itself.

### Call a function through its module

*In the code:* `paths::config_file()`, `paths::log_dir()`...

For a function, `use` its module rather than the function itself: the call then shows
where it comes from.

```rust
use crate::paths;           // in config.rs
paths::config_file()        // clearly the app's paths, not a local function
```

Types and traits are imported directly instead (`use crate::matrix::Matrix;`): their name
is already clear on its own.

In main.rs, `paths::log_dir()` needs no `use` at all: `mod paths;` already puts the module
in scope there (main.rs is the crate root). `use crate::paths;` would even fail: the name
would be defined twice.

### Import paths: `std`, `super::`, `crate::`

*In the code:* the `use` blocks of every file (e.g. weather.rs)

```rust
use std::time::Duration;            // 1. the standard library

use anyhow::{Context, Result};      // 2. external crates
use serde::Deserialize;

use super::{AppContext, State};     // 3. this crate: the parent module...
use crate::matrix::Matrix;          //    ...and the others, from the crate root
```

- **Three groups**, separated by a blank line. `cargo fmt` sorts the lines inside a group,
  but doesn't make the groups (that option is nightly-only).
- **`std::`, not `core::`**: `core` is the part of `std` that works without an OS, used by
  `no_std` crates such as embedded-graphics. Same types (`core::convert::Infallible` is
  `std::convert::Infallible`), but an app with `std` writes `std::`.
- **The original path, not a re-export**: `tokio::time::Duration` is `std::time::Duration`
  re-exported. Import it from `std` when it's the only thing needed; app.rs and feed.rs
  take it from `tokio::time` with the rest (`Instant`, `sleep`...).
- **`super::` for the parent module** (`states/weather.rs` → `states.rs`, `matrix/display.rs`
  → `matrix.rs`), **`crate::` for the others**: `super::` shows the close link, and keeps
  working if the parent module is moved.

### `bool::then`

*In the code:* `ClockState::new`, build.rs

```rust
config.enabled.then(Self::default)  // true → Some(Self::default()), false → None
is_armv6.then_some("CPU_ARCH_FLAGS=...")  // same, with a value instead of a function
```

`then` only calls its function when `true`. `then_some` gets a value built either way.

### Iterator chains

*In the code:* `App::next_state`

```rust
let next = (1..=count)                             // 1, 2, ..., count
    .map(|offset| (self.current + offset) % count) // the next indexes, wrapping around
    .find(|&index| self.states[index].is_ready()); // the first ready one, or None
```

Iterators are lazy: `find` stops at the first match, and nothing is allocated.

### `let ... else`

*In the code:* `WeatherState::draw`, `CalendarState::draw`

```rust
let Some(forecast) = self.forecast.latest() else {
    return; // must leave: return, break, continue or panic
};
// `forecast` is usable here, without nesting
```

### Chaining on `Option`

*In the code:* `Feed::latest`, `opt_c_ptr`

```rust
self.rx.borrow()                  // &Option<Fetched<T>>
    .as_ref()                     // Option<&Fetched<T>>: borrows instead of moving out
    .filter(|f| ...)              // `None` if too old
    .map(|f| Arc::clone(&f.data)) // Option<Arc<T>>

s.map_or(std::ptr::null(), CStr::as_ptr) // None → null, Some(s) → s.as_ptr()
```

### `as` casts

*In the code:* `Matrix::new` (`PANEL_HEIGHT as i32`), `OriginDimensions for Canvas` (`width as u32`),
`ClockState::draw` (`f64` → `u32`)

`as` never fails: a value that doesn't fit is silently truncated or wrapped
(`300_i32 as u8` is `44`). A float is rounded toward zero, and clamped to the target's
range (`2.9_f64 as u32` is `2`, `-1.0 as u32` is `0`). Fine for small, known values. For anything else, use a checked
conversion: `u8::try_from(x)?`.

### `matches!`

*In the code:* `events_are_read_from_the_api_response`

`matches!(value, pattern if condition)` returns a `bool`: handy to check an enum variant
and its fields in a single `assert!`.

## Logging

*In the code:* `init_logging`, every `info!`, `warn!`...

- **Levels**: `error!` when something is lost (a state disabled, a fatal error), `warn!`
  when it is handled (retried later, defaults used), `info!` for what the app does,
  `debug!` and `trace!` for details (hidden by default).
- **No prefix in the messages**: each line shows its *target*, the module path
  (`PIxel::states::weather`).
- **`RUST_LOG`** changes the filter without recompiling:

  ```sh
  RUST_LOG=debug ./PIxel                               # everything, dependencies included
  RUST_LOG=PIxel=debug ./PIxel                         # the app only (target = binary name)
  RUST_LOG=info,PIxel::states::calendar=trace ./PIxel  # one module in detail
  ```

- **Non-blocking file writes**: a dedicated thread writes the lines, so logging never
  waits for the SD card. Its `WorkerGuard` writes the last lines when dropped (see
  [`let _guard`](#let-_guard-keeps-a-value-alive-let-_-drops-it)).
- **The console writes block**: the console layer writes to stdout right away, in the
  thread that logs (under systemd: to the journal). Usually fast, but it can wait: never
  log in `draw`. If needed, wrap stdout like the file: `tracing_appender::non_blocking(std::io::stdout())`.
- **Line formats** (on `fmt::layer()`): full (default), `.compact()`, `.pretty()`, `.json()`
  (needs the `json` feature). Both layers use the same chain: only the writer and the
  colors differ.
- **Never log a secret** (OAuth2 token, credentials).

## Build and cross-compilation

### What build.rs does

*In the code:* build.rs

Cargo runs `build.rs` before compiling the crate. Here, it:

1. compiles the C++ library with `make`, in `OUT_DIR` (a build directory Cargo gives to
   each target);
2. tells Cargo how to link it, by printing `cargo:` lines:

   ```text
   cargo:rustc-link-search=native=<dir>    where librgbmatrix.a is
   cargo:rustc-link-lib=static=rgbmatrix   link it (lib<name>.a)
   cargo:rustc-link-lib=stdc++             and the C++ standard library it needs
   cargo:rerun-if-changed=<path>           run build.rs again only when this changes
   ```

3. generates the Rust bindings of the matrix C API with bindgen (from `deps/wrapper.h`),
   in `OUT_DIR/bindings.rs`, included by ffi.rs.

### Cross-compiling for the Pi Zero

*In the code:* build.rs, Makefile (`make target`), Cross.toml, Dockerfile.cross

The Pi Zero W is an ARMv6 (`arm-unknown-linux-gnueabihf`). `cross` builds in a Docker
container that holds the ARM toolchain.

- make only reads `CC` and `CXX`: build.rs sets them from `CROSS_TOOLCHAIN_PREFIX`, or make
  would use the x86 compilers of the container.
- `-march=armv6` is only added for the Pi Zero target.
- One build directory per target (`OUT_DIR`) keeps the host build (for rust-analyzer) and
  the ARM build apart.

### Two different LTOs

*In the code:* build.rs (`LTO_FLAGS=`), Cargo.toml `[profile.release]`

- The C++ library is built **without** GCC's LTO: its objects would contain GCC bytecode,
  which the Rust linker can't read.
- The Rust code is built **with** LTO in release (`lto = true`, `codegen-units = 1`): a
  smaller and faster binary, for a slower build.

### rustls rather than OpenSSL

*In the code:* Cargo.toml (`reqwest` features)

reqwest and yup-oauth2 both use rustls (TLS written in Rust): a single TLS stack, and no
OpenSSL to cross-compile.

## Performance on the Pi Zero

A single 1 GHz ARMv6 core and 512 MB of RAM. At 30 fps, a frame has 33 ms.

- **Nothing slow in `draw`**: no I/O, no waiting, no decoding. Prepare the data in the
  constructor, or in the background `fetch`.
- **No allocation per frame when it can be avoided**: `ClockState` formats its text again
  only when the minute changes (once every 1800 frames).
- **Styles are `const`**: built at compile time.
- **Only the current frame of an animation is read**: 2048 pixels of the `EARTH` strip,
  not the whole strip (see [Images embedded in the binary](#images-embedded-in-the-binary-include_bytes--const-fn)).
- **Shared data isn't copied**: `Feed::latest` returns an `Arc` clone.
- **The network is in background tasks**, with a timeout.
- **Late frames are skipped**, not drawn in a burst (`MissedTickBehavior::Skip`).
- **One C call fills the screen** (the `DrawTarget::clear` override), instead of 2048
  `set_pixel` calls.
- **Logging to the file doesn't block** (non-blocking file writer). The console writes do:
  nothing is logged per frame.
- **Release profile**: LTO and `codegen-units = 1`.

## Tests

*In the code:* the `tests` modules of config.rs, weather.rs and calendar.rs

```rust
#[cfg(test)]      // compiled by `cargo test` only
mod tests {
    use super::*; // everything of the parent module, private items included

    #[test]
    fn forecast_is_read_from_the_api_response() { /* ... */ }
}
```

- Unit tests live next to the code, so they can test private items.
- Test names are sentences: a failing test reads as the broken rule.
- Parsing is tested with real API responses (shortened), in raw strings `r#"..."#`: no
  need to escape the `"`.
- Each edge case gets its own test: no day in the response, no `items`, an event without
  start, a typo in the config.
- A test must not depend on the machine: `events_are_read_from_the_api_response` compares
  instants, not local times.
- `.unwrap()` is fine in tests: a panic is a failed test.
- `serde_json` is in `[dev-dependencies]`: only compiled for the tests.

Run them on the PC with `cargo test`: no Pi needed.

## Project conventions

- **Comments**:
  - `//!` at the top of a module: what it is for;
  - `///` on items: what it does, with a `# Errors` section when it returns a `Result`, and
    `# Safety` for an `unsafe fn`;
  - `//` in the code: only the *why* the code can't tell;
  - `// SAFETY:` before every `unsafe` block;
  - the Rust concepts are explained here, not in the code.
- **Sections**: only in the long files, one-line banners named after what follows: a type
  (`// ===== App =====`), its impls (`// ===== impl WeatherState =====`) or a role
  (`// ===== Background task =====`). `mod tests` needs none: it is already a section.
- **Formatting**: `cargo fmt` before committing (rules in `rustfmt.toml`).
- **Lints**: `cargo clippy`, with no warning left.
- **Imports**: three groups (`std`, external crates, this crate), `super::` for the parent
  module and `crate::` for the others (see [Import paths](#import-paths-std-super-crate)).
- **Errors**: `anyhow::Result` with `context`, messages in lowercase without a final period.
- **Panics**: `expect("... should ...")` in lowercase, saying what should have been true
  (see [When to panic](#when-to-panic)).
- **Logs**: a capital letter, no final period (no official Rust rule here: a project choice).
- **Constructors**: `new`, returning `Self`, `Result<Self>` if it can fail, or `Option<Self>`
  for a state that can be turned off.
- **`Self`**: inside an `impl`, rather than repeating the type's name (see
  [`Self` inside an `impl`](#self-inside-an-impl)).
